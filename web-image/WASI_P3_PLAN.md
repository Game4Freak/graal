# Plan: WASI 0.3 and Component Model Support for Web Image

Status: in progress, last updated 2026-10-26 (Phases 0 to 5 done except cancellation, error-context, host-side tests of stream and resource exports, and CI; Phase 6 open).
This document records the plan for teaching the Native Image WebAssembly backend (Web Image) to produce a WebAssembly component that targets WASI 0.3 (also known as WASI Preview 3, or "p3") and to generate bindings for custom WebAssembly Interface Type (WIT) interfaces, including `async` functions, `stream<T>`, and `future<T>`.

## Goals

1. `native-image --tool:svm-wasm --target=wasi` (name to be decided) produces a single `app.wasm` **component** that implements `wasi:cli/command@0.3.x` and runs under Wasmtime 46+ with no JavaScript wrapper.
2. The Java standard library works on top of WASI 0.3 interfaces: standard streams, file system, clocks, random, environment, arguments, and exit.
3. A binding generator ("bindgen") lets an application import and export custom WIT interfaces, including the Component Model async primitives, from plain Java.

## Non-Goals (for now)

- Preemptive or cooperative threads (`wasi:threads`); the Wasm backends are single-threaded today and WASI 0.3 ships threads in a later 0.3.x release.
- Running components in the browser or Node.js (that is what `jco` transpilation is for; it can be a follow-up test target).
- Replacing the existing JavaScript host (`compat`, `io`, `convert` import modules). The JS host stays the default; WASI becomes a second host.

## Current State of the Backend (as of this commit)

- Three backends are selected through `-H:Backend=` (`JS`, `WASM`, `WASMGC`) in `com.oracle.svm.hosted.webimage.options.WebImageOptions.CompilerBackend`, each bound to a `Platform` class under `com.oracle.svm.webimage.platform`.
  `-H:Backend` is only honored by the `mx web-image` launcher.
  Under `native-image --tool:svm-wasm`, `WebImagePlatformInjector` (`hosted/webimage/WebImagePlatformInjector.java:44-53`) always forces `WASMGC`.
- `WASM` is the linear-memory backend (`WebImageWasmLMPlatform`, `WebImageWasmLMBackend`, `WebImageWasmLMCodeGen`) with its own GC under `wasm/gc/`.
  It already exports `memory`, `malloc`, and `free` (see `wasm/gc/WasmAllocation.java:223-229` and `WebImageWasmLMCodeGen.java:110`), which is most of what the Canonical ABI needs.
  It does **not** support `@JS` bodies (see `fs/FileSystemInitializer.java:92-96`).
- `WASMGC` is the GC backend (`WebImageWasmGCPlatform`); objects live in Wasm GC structs, not linear memory, and cross the JS boundary as `externref`.
- All host interaction goes through five JS-provided import modules:
  - `compat` (math helpers), `io` (`printBytes`/`printChars`, LM only), and `convert` (`proxyCharArray`, GC only), declared in `hosted/webimage/wasm/WasmImports.java`.
  - `interop`: one import per `JSSystemFunction` (`Date.now`, `runtime.setExitCode`, cwd, args, and others), declared in `hosted/webimage/wasm/WasmJSCounterparts.java:71,149-157` and triggered by `JSCallNode` constants (`com.oracle.svm.webimage.functionintrinsics.JSCallNode:60-121`).
  - `jsbody`: one import per `@JS` method body (GC only), `WasmJSCounterparts.java:77,163-189`.
  The JS side is generated by `WebImageWasmCodeGen.emitBootstrapDefinitions()` plus the resource scripts `wasm/codegen/runtime/wasm-bootstrap.js`, `wasm-imports.js`, `wasm-run.js` for each backend, and the shared `codegen/runtime/{runtime,log-console,load-cmd-args,cwd}.js`.
- Standard library glue lives in `com.oracle.svm.webimage` (`print/`, `fs/`, `posix/`, `substitute/system/`, `WebImageSystemPropertiesSupport`, `WebImageJavaMainSupport`).
  Today: stdin is unimplemented (`JSFunctionIntrinsics.readBytesFromStdIn` throws), the environment is always empty (`Target_java_lang_ProcessEnvironment_Web`), `SecureRandom` is backed by `Math.random`, time comes from `Date.now`/`performance.now`, and the file system is an in-memory NIO file system (`WebImageNIOFileSystem`, backed by the shaded `jimfs` library, `SVM_WASM_JIMFS`).
- Output is assembled from text format by Binaryen's `wasm-as` 119 (`wasm/codegen/WasmAssembler.java`, `BinaryenCompat.java`), with wabt's `wat2wasm` as an alternative; the toolchain check pattern there (`-H:-CheckToolchain`, path options, smoke test `.wast` files) is the model for adding `wasm-tools`.
  Nothing in the tree calls `wasm-opt`, `wasm-tools`, or `wasmtime`.
- Tests run through `mx unittest JS_JTT_Spec_Test` (or `mx gate --tags webimagespectest --backend WASM|WASMGC`) with the `WEBIMAGE_TESTS` distribution.
  `WebImageTestUtil.runJS` executes the output with Node (`NODE_EXE`, system property `webimage.test.js`); the hooks for a Wasmtime runner are `WebImageTestOptions` and `WebImageTestUtil.runJS` in `com.oracle.svm.hosted.webimage.test.util`.
  The in-repo CI (`web-image/ci/ci.jsonnet`) runs only `webimagebuild` and `webimageunittest`; there is no Wasm-backend spec-test job to copy.
- The hosted option list in `mx.web-image/mx_web_image.py:69-121` (`ProvidedHostedOptions`) is hardcoded and checked by the `webimageoptions` gate tag; every new option must be added there.
- There is **no** mention of WASI, WIT, or components anywhere in `web-image/` or `substratevm/` today, apart from a note in `docs/get-started.md:91-93` that `wasmtime` cannot run the output.

## Key Design Decisions

### Build on the linear-memory backend

The Canonical ABI lifts and lowers values through linear memory (`memory` export, `cabi_realloc`, UTF-8 or UTF-16 strings).
The Component Model's GC integration (the `gc` canonopt) is still a gated future feature, so a WasmGC core module cannot be wrapped into a component yet.
The WASI target therefore starts on the `WASM` (linear-memory) backend.
Keep the host abstraction backend-neutral so the `WASMGC` backend can follow once runtimes accept GC types in components.

### Synchronous first, async second

WASI 0.3 functions are declared `async`, but a component may still call them with a **synchronous lowering** (the call blocks the caller's task until the host completes it) and may export `wasi:cli/run` with a synchronous lift.
This is the only mode that works for the Java standard library, whose I/O APIs are blocking and run on a single stack.
Native async (callback-based exports, `[async-lower]` imports, `waitable-set.wait`) is introduced only for user-defined WIT interfaces in the bindgen phase.

### Represent WIT with a small IR, not strings

Bindgen reads the WIT package as JSON produced by `wasm-tools component wit --json` and converts it into a Java model (`WitPackage`, `WitInterface`, `WitFunction`, `WitType`).
The same model drives both the standard library bindings (phase 2) and user bindings (phase 4), so there is one Canonical ABI implementation.

### Reuse external tooling instead of reimplementing it

The image builder shells out to `wasm-tools` for `component embed` and `component new`, mirroring how it already calls `wasm-as`.
Reimplementing the component encoder in Java is possible later but is not on the critical path.

### Phase 4: Bindgen for Custom WIT Interfaces (synchronous)

User-facing API, in the SDK package `org.graalvm.webimage.api` or a new `org.graalvm.wasm.component.api`:

- Build option `-H:Wit=<dir-or-file>` and `-H:WitWorld=<name>` selecting the world the image implements.
- A source generator (Java program or annotation processor, run from the `mx` build or a Maven/Gradle plugin) that turns the WIT JSON into Java interfaces and records:
  - WIT `record` becomes a Java `record`, `variant` and `enum` become sealed interfaces/enums, `option<T>` becomes `Optional<T>` or nullable, `result<T, E>` becomes a sealed `Result<T, E>`, `list<T>` becomes arrays or `List<T>`, `string` becomes `String`, `resource` becomes a Java class holding a handle with `close()`.

  - Exported interfaces become Java interfaces the user implements and registers with `@WitExport`.
- Image-builder support (`WitBindgenFeature`):
  - For each `@WitImport`, synthesize a core import with the Canonical ABI name (for example `wasi:cli/stdout@0.3.0#set-stdout`) and a graph that lowers arguments into linear memory, calls the import, and lifts the results.
  - For each `@WitExport`, synthesize an exported core function with the Canonical ABI signature plus the `cabi_post_*` cleanup export where needed.
  - Emit the `component-type` custom section via `wasm-tools component embed` so `component new` can type-check the module.
- Choose `string-encoding=utf16` for the Canonical ABI options to avoid transcoding Java strings; measure against `utf8` later.

### Phase 5: Async Support in Bindgen

Java has no language-level async, and the single-threaded Wasm backends cannot switch stacks, so async maps onto a stackless, callback-driven design.

- **Async imports**: generate `[async-lower]` variants returning a `WitFuture<T>` (a minimal `CompletionStage`-like type) when the user declares the Java method as returning `WitFuture<T>`.
  Synchronous lowering remains the default for convenience.
- **Async exports**: lift with the `async` and `callback` canonopts.
  The generated export runs the Java method once; if the method returns a completed `WitFuture`, the binding calls `task.return` and reports `EXIT`.
  Otherwise the binding registers the pending waitables in a `waitable-set` and returns `WAIT`.
  The generated `callback` export dispatches the event to a Java scheduler (`WitTaskScheduler`) that completes the corresponding `WitFuture`, runs continuations, and returns the next code.
- **Streams and futures**: `stream<T>` maps to `WitReadableStream<T>` and `WitWritableStream<T>` with both blocking (`read(T[])`) and async (`readAsync` returning `WitFuture`) methods on top of `stream.read`/`stream.write`; `future<T>` maps to `WitFuture<T>` plus `WitFutureWriter<T>`.
- **error-context**: expose as a Java exception type carrying the debug message.
- **Cancellation**: support `task.cancel` and `subtask.cancel` through `WitFuture.cancel()`.
- Provide an optional blocking bridge: a `WitFuture.join()` that uses `waitable-set.wait` and is only legal from a synchronously lifted export (checked at run time).

Deliverable: an async echo and a streaming example (for example a `wasi:http/proxy` handler) validated with Wasmtime's `component-model-async` enabled.

- Two scheduler bugs found by the test: a finished handler must not un-join a dropped waitable, and the host reuses handle indices, so a handler is removed before it runs and re-registered only if still pending.
- Functions whose signatures use unsupported types (`stream`, `future`, exported resources) are skipped with a comment instead of failing the generator, so `--include-wasi` produces bindings for the usable parts of the WASI interfaces.

Status (2026-10-26), step 2 done: `stream<T>` and `future<T>` values.

- SDK: `WitStream<T>` (created by Java with both ends, or received with a readable end; `read(max)`, `readBytes(max)`, `write(list)`, `writeBytes(bytes)`, `close()`, all returning `WitFuture`), `WitPromise<T>` for `future<T>` (`read()`, `write(value)`), `WitStreamOps`/`WitFutureOps` for the per-function built-ins, and `WitElementCodec<T>` (with `BYTE` and `UNIT`) for element marshalling.
- Generator: the built-ins are indexed per function in the post-order used by `wasm-tools` (`asyncTypes`), emitted as `@WitImport` natives plus an ops table (`OPS_<FN>`) and `create<Fn>Stream<i>()`/`create<Fn>Future<i>()` factories; `Abi` helpers of types that contain streams or futures take the table and a base index, so streams nested in tuples, records, variants, options, results, and lists resolve to the right built-in; element codecs are generated per element type. Built-ins of exported functions are imported from `[export]...` modules. Exported WASI interfaces (`wasi:cli/run`) are never generated because the runtime implements them.
- Verified (`streamtest/`): `main` reads all of stdin through the generated `Stdin.readViaStream()` (a `tuple<stream<u8>, future<result<_, error-code>>>`) and writes through `Stdout.writeViaStream` with a Java-created stream, awaiting both futures; the generated bindings of all WASI 0.3 interfaces compile without skips. Exports with stream parameters or results (`numbers`, `total`) build but cannot be invoked from the Wasmtime CLI, whose value syntax has no streams; a host-side test (Rust or another component) is still to do.
- Generated adapters print uncaught exceptions of exports to stderr before the trap (`reportUncaught`).
- Host-side tests: `jco` 1.39 cannot translate WASI 0.3 components yet ("failed to translate component"), and the Wasmtime CLI cannot pass streams or resources, so stream and resource exports need a host that embeds Wasmtime (a small Rust program with the `wasmtime` crate) or a later `jco`.
- Still open in Phase 5: cancellation (`subtask.cancel`, `TASK_CANCELLED`) and `error-context`.

Design notes (2026-10-26), refined from what Phases 1 to 4 established:

- Imports: the generator already knows every function's flat signature. For an `async func` import, emit a second native with the `[async-lower]` prefix; its core signature is the flat params followed by a return pointer for the lifted result, and it returns `i32` (`subtask status` packed as `(subtask handle << 4) | state`). If the state is `RETURNED`, lift from the return pointer immediately. Otherwise register the subtask handle in a `WitFuture` and return it; the result pointer must stay allocated until the subtask returns (allocate it outside the arena and free it in the completion handler).
- A runtime scheduler (`WitTaskScheduler`, runtime project) owns one `waitable-set` and a map from waitable handle to continuation. `WitFuture.join()` blocks with `waitable-set.wait` and dispatches events until its own completes; this is the only blocking primitive and is legal from synchronously lifted exports, which is what the runtime uses today. `subtask.drop` after `RETURNED`.
- Exports: lift with `[async-lift]` plus `[callback]` (names `[async-lift]<export>` and `[callback][async-lift]<export>`). The adapter runs the Java method once; the method returns a `WitFuture<T>`. If it is already complete, call `[task-return]<export>` with the lowered flats and return `EXIT` (0). Otherwise store the pending future in `context.set` (slot 0) and return `WAIT | (set << 4)` for the scheduler's waitable set. The callback export receives the event, dispatches it through the scheduler, and repeats the check. Because the whole runtime is single-threaded and the host only calls the callback when no Java frame is active, this is a stackless state machine over `CompletableFuture`-style continuations in Java code.
- Streams and futures: `WitReadableStream<T>`/`WitWritableStream<T>` wrap the handle plus the element type's `Abi` helpers (lower/lift of one element into a buffer of `n * size`). `read(T[])`/`write(T[])` block (asynchronous builtin plus `WitFuture.join()`), `readAsync` returns a `WitFuture<Integer>`. `future<T>` becomes `WitFuture<T>` (readable end) and `WitFutureWriter<T>`. Element helpers for the stream type come from `Abi` as for lists.
- `error-context`: `[error-context-new-utf8]`, `[error-context-debug-message-utf8]`, `[error-context-drop]` wrapped in `WitErrorContext extends Exception`.
- Cancellation: `[subtask-cancel]` from `WitFuture.cancel()`, `[task-cancel]` when an export is cancelled by the host (callback event `TASK_CANCELLED`).
- Generated Java shape: `async func` imports return `WitFuture<T>`; `async func` exports are declared in the Java interface as returning `WitFuture<T>`; `stream<T>` parameters and results use the stream wrappers.
- Required Wasmtime flags: none for the async lift/lower and stream built-ins (verified in Phase 0 with default flags on Wasmtime 50); `-W component-model-async-stackful` is not needed.
- Prerequisite in the builder: `WitBindingFeature` must allow the `[async-lift]`, `[callback]`, and `[task-return]` export and import names (they are plain `@WitExport`/`@WitImport` names, so no change is expected) and the codegen must keep the exported Java method's core signature intact.

### Phase 6: Hardening and Follow-ups

- Size and performance: run `wasm-opt` on the core module before `component new`; compare against the JS host.
- Debugging: keep DWARF or name section support through `wasm-tools` (`--debug` style flags).
- Consider a WasmGC path once the `gc` canonopt stabilizes.
- Consider contributing a `graalvm-java` guest generator to upstream `wit-bindgen` once the Java API shape is stable, so users can generate bindings without the image builder.
- Evaluate `jco transpile` to run the same component in Node.js and the browser.

## Open Questions

- Stdout stream lifetime: the runtime creates one stream per fd for the whole run and awaits the returned future on exit. Confirm this is the intended usage and measure the cost of a `waitable-set.wait` per write when the host blocks.
- Which world to implement by default: `wasi:cli/command` only, or also a "library" world with no `run` export for reactor-style components.
- Exposure through `native-image` (decided 2026-10-26): the dedicated `--tool:svm-wasi` macro (component `niwasi`, distribution `NATIVE_IMAGE_WASI_SUPPORT`) passes `-H:Backend=WASI` through the macro's `Args`, and `WebImagePlatformInjector` honors it; other backend values still fall back to WasmGC under `native-image`.
- How `@JS`-based libraries (for example the existing `JSObject` API) should behave when a user targets WASI: hard error versus best-effort stubs.
- Whether bindgen should run inside the image builder (no extra build step, but no IDE completion) or as a separate code generator (extra step, but normal Java tooling).
  The plan above assumes a separate generator for sources plus in-builder lowering.
